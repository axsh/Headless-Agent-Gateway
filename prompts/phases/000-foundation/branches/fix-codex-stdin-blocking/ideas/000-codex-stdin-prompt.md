# 仕様書: `codex` CLI の標準入力によるプロンプト受け渡しとデバッグログの強化

## 背景

`arctic-tern` の `agentservice` を通じて `codex` エージェントを実行する際、Windows環境において長文のプロンプト（特に多数の画像パスを含む場合や、ユーザーからの長文メッセージ）を渡すと、コマンドライン引数の制限（8,191文字）により引数が切り捨てられ、`codex` CLI が不正な状態で起動される問題が発生しています。

切り捨てられた結果、クォーテーションが閉じられていないなどの不完全な引数を受け取った `codex` は、不足分を補うためか、あるいは対話モードと誤認して標準入力からの読み取りを試みます。しかし、非対話環境であるため標準入力が閉じられていたり、期待される入力が得られなかったりすることで、`Reading additional input from stdin...` というエラーを出力してクラッシュまたはハングアップします。

また、現状では `codex` の標準エラー出力や、JSONL形式以外の標準出力が十分にログに記録されておらず、問題発生時の原因特定が困難です。

## 要件

1.  **プロンプトの受け渡し方法の改善**:
    - `codex exec` コマンドに引数としてプロンプトを渡すのではなく、標準入力 (stdin) を通じて渡すように変更する。
    - コマンドライン引数には `-` を指定し、標準入力から指示を読み込むように `codex` に指示する。
2.  **デバッグログの拡充**:
    - `codex` の標準エラー出力 (stderr) をリアルタイムでスキャンし、デバッグログ (`Debug` レベル) に出力する。
    - 標準出力 (stdout) において、JSONLイベントとして解析できなかった行を、現在の `Trace` レベルから `Debug` レベルに引き上げて出力する。
3.  **互換性と安定性**:
    - `claudecode` (Claude Code) についても同様の修正が可能か検討し、必要であれば適用する（今回は `codex` を優先）。
    - プロンプトを書き込んだ後は標準入力を適切に閉じ、`codex` が指示の終了を検知できるようにする。

## 実現方針

### `codex` アダプターの修正

`shared/libs/go/codingagent/codex/process.go` を以下の通り修正します。

1.  **`BuildArgs` の変更**:
    - 第1引数の `prompt` が空でない場合、引数の末尾に `prompt` 文字列そのものではなく `-` を追加する。
2.  **`StartProcess` の変更**:
    - `exec.CommandContext` を作成した後、`cmd.Stdin` に `cfg.Prompt` を流し込む `io.Reader` を設定する。
    - `cmd.StderrPipe()` を使用して、標準エラー出力をリアルタイムに読み取るゴルーチンを追加する。
    - 読み取った stderr は `log.Debug` で出力しつつ、既存の `stderrBuf` にも蓄積して、プロセス終了時のエラー報告に使用できるようにする。
    - stdout のスキャンループにおいて、`ParseExecEvent` が `nil` を返した場合（解析不能な行）のログレベルを `Debug` に変更する。

### `claudecode` アダプターの検討

`claude` (Claude Code) のヘルプによると、`-p` オプションや位置引数でのプロンプト指定が主ですが、標準入力からの読み込みについても同様の対策が必要か、実装を確認します。
※ `claude` は `-p` を使わない場合に標準入力を待つ挙動があるため、`-p` 引数を削除して stdin に書き込む方式が機能するか検証します。

## 検証シナリオ

### 自動テスト

1.  **長文プロンプトテスト**:
    - 8,192文字を超えるプロンプトを作成し、`codex` セッションを開始する。
    - 正常にエージェントが起動し、応答が返ってくることを確認する。
2.  **エラーログ出力テスト**:
    - 意図的に不正な設定を与えて `codex` を起動し、標準エラー出力の内容が `Debug` ログに出力されることを確認する。

### 手動確認

1.  Windows環境の Git Bash にて、`tern-server` を起動し、クライアントから画像付きメッセージを送信して、クラッシュが発生しないことを確認する。
2.  サーバーログにおいて `CLI stderr line` や `unhandled codex event type` が適切に出力されているか確認する。
