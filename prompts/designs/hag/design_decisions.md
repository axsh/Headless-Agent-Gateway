# HAG LLM Backend 設計決定事項

本ドキュメントは、vv4参照実装の調査とレビュー議論を通じて決定された設計方針をまとめたものである。
各項目は「決定事項」「理由」「将来の展望」の3軸で構成する。

決定日: 2026-06-03

---

## 1. アーキテクチャ

### DD-001: 3層構造の維持

- **決定**: vv4の3層構造 (Interface / Driver / Deployment) をそのまま維持する
- **理由**: 各層が明確に異なる責務を担い、差し替え可能性を確保するため
- **将来**: 新しいDriverやDeployment方式の追加が容易

### DD-002: インターフェース名は LLMGatewayBackend を採用

- **決定**: 設計ドキュメントの `LLMProvider` ではなく、vv4の `LLMGatewayBackend` を採用する
- **理由**: `LLMProvider` だとOpenAI/Anthropicといったプロバイダ自体をイメージするが、実体はBifrostBackend等のゲートウェイバックエンド。`LLMGatewayBackend` の方が実体に合っている
- **やらないこと**: `LLMProvider` へのリネームは行わない

### DD-003: ライフサイクルは New + Launch パターン

- **決定**: インスタンス生成は `New` (メモリ上の準備完了)、起動は `Launch` (明確な起動フェーズ)、停止は `Shutdown` とする
- **理由**: `Initialize` はWeb API露出時の表現として適切だが、`New`/`Launch` の方がGoの慣習に合い、かつ明確な起動フェーズを区別できる
- **やらないこと**: `Initialize` パターンは採用しない

### DD-004: LLMClient と LLMGatewayBackend は統合しない

- **決定**: 2つのインターフェースは別々に維持する
- **理由**: `LLMGatewayBackend` はサーバサイドのエンドポイント定義、`LLMClient` はそれを使うクライアントの定義。コンテキストが異なる
- **将来**: ただし DD-005 の通り、llmadapter層自体が不要なため、`LLMClient` は移植しない

### DD-005: llmadapter層は移植しない

- **決定**: vv4の `llmadapter` パッケージのうち、`LLMClient`, `ProviderAdapter`, `Client`, `GatewayAdapter`, `factory.go` は移植しない
- **理由**: HAGの主目的はCoding Agentの管理であり、LLMへの直接API呼び出し (ChatCompletion) はCoding Agent CLIが内部的に行う。HAGがLLMを直接呼ぶ必要がない。vv4でこれが必要だったのはTask Engineの各Logic (LLM:*) がLLMを直接呼んでいたためで、HAGには該当機能がない
- **移植するもの**: `gateway/` サブパッケージ全体と `schema/` サブパッケージ

### DD-006: Backend Driverは2種類

- **決定**: `BifrostDriver` と `PassthroughDriver` (L4転送) の2種のみ
- **理由**: `DirectDriver` (特定プロバイダへの直接HTTP接続) は、BifrostDriverで単一プロバイダ構成にすれば同等の機能が得られるため不要
- **やらないこと**: `DirectDriver` の実装

### DD-007: Bifrost SDKは差し替え可能にする

- **決定**: Bifrost SDKへの依存を抽象化し、将来的に別のバックエンドエンジンへの差し替えを可能にする
- **理由**: Bifrost SDKの将来的な方向性変更やライセンス変更に備える
- **実装**: `LLMGatewayBackend` インターフェースを通じた抽象化で対応

### DD-008: Bifrost SDKバージョンは常に最新追随

- **決定**: Bifrost SDKは常に最新バージョンに追随する
- **理由**: 新機能・バグ修正の恩恵を受けるため

## 2. HTTP Proxy / API互換性

### DD-009: Anthropic Messages APIは厳密にAnthropic公式準拠

- **決定**: SSEストリーミングを含め、Anthropic公式APIフォーマットに厳密に準拠する
- **理由**: Claude Code CLIがAnthropic APIフォーマットのみ理解するため。独自拡張は無視されるかパースエラーの原因になる
- **やらないこと**: SSEイベントの独自拡張は一切行わない

### DD-010: OpenAI Chat Completions ストリーミングはCodex対応時

- **決定**: OpenAI Chat Completions APIの `stream: true` 対応はCodexをCoding Agentにする際に実装する
- **理由**: 現時点ではClaude Code対応が優先
- **将来**: 実装時はTODOコメントを配置し、将来の実装ポイントを明示する

### DD-011: ChatCompletion APIは不要、Responses APIのみ

- **決定**: OpenAI Chat Completions APIの長期サポートは不要。Responses APIのみ対応する
- **理由**: Chat Completions APIは将来非推奨になる可能性がある

### DD-012: /v1/models はmodel_profilesから実際の一覧を返す

- **決定**: vv4のように空リストを返すのではなく、`model_profiles.yaml` から実際のモデル一覧を返す
- **理由**: クライアント (Agent CLI) がモデル一覧を参照できるようにするため

### DD-013: デフォルトプロバイダ補完はエラーにする

- **決定**: モデル名にプロバイダが指定されていない場合、`openai` をデフォルトとする補完は行わず、エラーを返す
- **理由**: 暗黙のルールは避け、プロバイダは常に明示的に指定させる

### DD-014: Provider と Model は別フィールドで定義

- **決定**: リクエストの `provider` と `model` は文字列パース (`provider/model`) ではなく、別々のフィールドとして定義する
- **理由**: 文字列にフォーマットの暗黙ルールを入れない方が明確

### DD-015: テキスト→Tool Callフォールバック変換は必須

- **決定**: ローカルLLM (Ollama等) で tool_calls を返さないモデルに対するテキスト→Tool Call変換を実装する
- **理由**: ローカルLLMも使用対象であり、この変換がないとtool call不可となる
- **実装方針**: フォールバック挙動はモデル毎に `model_profiles.yaml` で設定可能にする。他のモデルで邪魔になるフォールバックもあるため、モデル設定で有効/無効を切り替える

### DD-016: ヘルスチェックエンドポイント

- **決定**: `GET /` は `200 OK` + エンドポイント一覧インデックスを返す。`/health` は状態をJSONで返す
- **理由**: Claude Code CLIがベースURL到達性チェックのために `GET /` で `200 OK` を要求する。`/health` は運用監視向け

### DD-017: エラーレスポンスはJSON形式

- **決定**: OpenAI/Anthropic互換のエラーレスポンスJSON形式を実装する。プロバイダからのエラーはLLM Gateway独自のエラーコードに変換して返す
- **理由**: Agent CLIがJSONエラーを期待する。プロバイダのエラー粒度は異なるため、Gatewayが責任を持って統一する
- **実装**: 原因のHTTPステータスコードはメッセージに含めて開示する (スタックトレース的な情報開示)

### DD-018: モデルフォールバック (サブセッション問題対応) はHTTP Proxyで実装

- **決定**: Claude Codeがサブセッションでmodel_profilesに存在しないモデル名を送信してくる問題へのフォールバックは、HTTPプロキシのリクエストハンドラ内で実装する
- **理由**: Bifrostのアカウント設定では吸収しきれないClaude Code固有の問題であり、リクエストハンドラが最も適切な介入ポイント

## 3. 統一スキーマ

### DD-019: マルチモーダル対応 (将来準備)

- **決定**: `UnifiedMessage` の `Content` フィールドにコンテントタイプ情報を持たせ、将来のマルチモーダル対応に備える
- **理由**: 最初から多数のメディアに対応する必要はないが、将来のために型構造として対応しておく

### DD-020: Reasoning制御はLLM Gateway側では不要

- **決定**: Reasoning (thinking) のリクエスト側制御はLLM Gatewayでは実装しない
- **理由**: Coding Agent経由で使う限り、Agent CLIが制御する領域であり、LLM Gatewayが介入する必要がない

---

## 4. 設定・シークレット管理

### DD-021: ModelProfilesConfig はvv4のスキーマをそのまま使用

- **決定**: `model_profiles.yaml` のスキーマはvv4のものをそのまま採用する
- **理由**: 実績のある設計であり、変更の必要がない
- **追加**: モデル毎の挙動設定 (フォールバック変換の有効/無効等) を追加する

### DD-022: weight フィールド (加重ルーティング) は不要

- **決定**: `model_profiles.yaml` のキー定義にある `weight` フィールドによる加重ルーティングは実装しない
- **やらないこと**: 複数APIキー間の加重ロードバランシング

### DD-023: governance.routing_rules は定義のみ残しTODO

- **決定**: 構造体の定義は `model_profiles.yaml` のスキーマに残すが、実装はしない。TODOコメントで目的と将来の実装方針を記述する
- **理由**: 興味深いアイディアではあるが、v1では不要。再度議論が発生した際に経緯が失われないようメモとして残す
- **将来のメモ**: CEL式によるリクエスト条件ベースのモデルルーティング・フォールバック制御。Bifrost SDKにもフォールバック機能があるため、独自実装の必要性は慎重に検討すること

### DD-024: AppConfig は専用構造体で最小限

- **決定**: HAG専用のコンフィグ構造体を用意し、vv4の `AppConfig` から最低限のフィールドのみ採用する
- **理由**: vv4はTask Engineやデータベース等の多くのフィールドを持つが、HAGには不要なものが多い

### DD-025: 設定ファイルのパス解決

- **決定**: コマンドラインオプションで設定ファイルパスを指定可能にする。デフォルトは `./config.yaml`
- **理由**: シンプルで一般的な慣習に従う

### DD-026: 設定リロードはAPIで即適用

- **決定**: ホットリロード (ファイル監視) ではなく、再設定APIの呼び出しで即適用する方式とする
- **理由**: ファイル監視は複雑さを増し、意図しないリロードが発生するリスクがある

### DD-027: マルチテナント必須

- **決定**: VaultStoreのマルチテナント対応は必須とする
- **理由**: チーム利用を想定するため

### DD-028: Vault参照形式は vault:// に統一

- **決定**: `vault://providers/{name}` 形式 (vv4形式) に統一する
- **やらないこと**: 設計ドキュメントの `vault:ollama_key` 形式は採用しない

### DD-029: 環境変数からのAPIキー読み込み対応

- **決定**: APIキーを環境変数から読み込む機能を実装する
- **理由**: 開発時の簡易セットアップのため

### DD-030: AES暗号化はオプショナル

- **決定**: VaultStoreのAES暗号化はオプショナル機能とする
- **理由**: Keyringバックエンド使用時はOS側の保護があるため二重暗号化は不要。ファイルバックエンドでの平文保存防止には有用

### DD-031: プロバイダ固有設定はBifrost SDKに委譲

- **決定**: Ollamaの接続URL設定など、プロバイダ固有の差異はBifrost SDKに委譲する。HAG側で個別対応しない
- **理由**: `model_profiles.yaml` の `network_config.base_url` で設定を渡せば、Bifrost SDKが適切に処理する
- **実装**: プロバイダ毎の特殊ケース対応コードはHAGに書かない

## 5. Rate Limiting

### DD-032: Rate Limitingはv1で必須

- **決定**: Rate LimitingはMVPに含める
- **理由**: ループ等ですぐにリミットエラーになる現象が実際に発生するため

### DD-033: Rate LimitingはBifrostに委譲

- **決定**: Bifrost SDKのRate Limiting機能を使用する。vv4の独自 `CompositeRateLimiter` / `TokenEstimator` / `TokenBucket` は移植しない
- **理由**: Bifrost SDKがPer-Tenant/Keyベースのレート制限、自動フォールバック等をネイティブサポートしている
- **やらないこと**: サポートしないバックエンドのための独自Rate Limiting実装

### DD-034: Rate Limitの粒度はプロバイダ別

- **決定**: Rate Limitingはプロバイダ毎に構築する。プロバイダ側がモデル別に計測しているならモデル名も渡して判定する
- **理由**: プロバイダ毎に考え方が異なるため、統一的な粒度は適切でない

### DD-035: トークン推定は不要

- **決定**: リクエスト前のトークン推定機能は実装しない
- **理由**: HAGはLLMを直接呼び出さないため (Coding Agent CLI経由)、トークン推定・管理の必要がない

## 6. セッション管理

### DD-036: SessionModelStore は削除

- **決定**: vv4の `SessionModelStore` (DB永続化のセッション毎デフォルトモデル管理) は移植しない
- **理由**: vv4のmain.goでもTODOコメントで無効化されている状態。Claude Codeがシングルショットで動作する場合はファイルにセッションが書き出されるため、DB管理は不要

### DD-037: モデルフォールバックは必須

- **決定**: Claude Codeがサブセッションでmodel_profilesに存在しないモデル名を送信する問題に対するフォールバック機構は必須
- **理由**: 実運用で動作しなくなる既知の問題

### DD-038: セッション毎のモデルルーティングは当然必要

- **決定**: HTTP Proxyは完全な並行処理であり、セッション毎に異なるモデルのルーティングは標準機能として実装する
- **理由**: Go標準の `http.Server` でリクエスト毎にgoroutineが起動される。リクエストの `model` フィールドで個別ルーティング。シングルスレッドではない

### DD-039: Gateway接続先は環境変数で注入

- **決定**: Agent CLIの起動時に、LLM GatewayのURLを環境変数 (`ANTHROPIC_BASE_URL` 等) として注入する
- **理由**: Agent CLI (Claude Code) がこの方式を要求する。セッション中のモデル切り替えとは別の議論であり、ここで言う「注入」はGateway接続先URLの指定のみを指す
- **注意**: 設計ドキュメントの「LLM設定注入」という表現は誤解を招くため、「Gateway接続先URL注入」に修正する

## 7. 可観測性

### DD-040: ロガーはvv4のloggerパッケージを使用

- **決定**: 標準 `slog` ではなく、vv4の `logger` パッケージを使用する
- **理由**: syslog出力対応等の機能が既にあるため

### DD-041: APIキーは下4桁のみ開示でマスク

- **決定**: ログ出力時、APIキーやシークレットは下4桁のみ開示し、残りをマスクする
- **理由**: デバッグ時にどのキーが使われたか特定できる程度の情報で十分

### DD-042: TraceレベルでのトレーシングはBifrostへの委譲+ログで実装

- **決定**: リクエスト/レスポンスのトレーシングはTraceログレベルで実装する
- **理由**: デバッグ時に有用

### DD-043: メトリクスはBifrostに委譲

- **決定**: レイテンシ、トークン使用量、エラー率等のメトリクス収集はBifrostの組み込み機能を使う。HAG独自のメトリクス収集は不要
- **実装**: Bifrostのメトリクス機能の有効/無効はLLM Gatewayの起動設定で制御できるようにする
- **将来**: メトリクスの参照方法として、コンテナでGUI/Prometheusを起動する実例を示す

## 8. テスト戦略

### DD-044: モックは使用しない

- **決定**: テストではモックを使用しない。実際のLLMプロバイダを使った統合テストを行う
- **理由**: モックは実際の挙動との乖離が生じやすく、メンテナンスコストが高い
- **やらないこと**: テスト用のモックバックエンド、`MemoryVaultBackend` 等の移植
